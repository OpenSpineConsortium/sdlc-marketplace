# Claim an issue

A claim is the first push of the branch `claude/<issue>`; whoever pushes first has the issue, because GitHub refuses the second push of the same name. The steps below are PROTOCOL.md's, in order. N stands for the issue's number throughout, D for the default branch (the name `git symbolic-ref --short refs/remotes/origin/HEAD` prints after `origin/`, or main when it prints nothing), and NAME for your name as a worker (PROTOCOL.md, Workers): a routine's or a worker in Actions' is the one its prompt gives; a person's sessions take the person's GitHub login, unless the session's environment sets SYMPHONY_WORKER to another, and `echo "${SYMPHONY_WORKER:-$(gh api user --jq .login)}"` prints it; in a cloud session without gh, the GitHub tools' own account (get_me) is the login. Your label is `worker:NAME`, and your settings, if you have a file, are `.github/symphony/workers/NAME.json`, whose area says where you prefer to work.

1. Fetch and read the board: `git fetch origin`, then `git fetch origin board && git show origin/board:STATE.md`. A clone made for one branch, as a cloud session's often is, fetches no other: where `git config --get-all remote.origin.fetch` does not print `+refs/heads/*:refs/remotes/origin/*`, run `git config --add remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'` before those fetches, since otherwise the board you read is the one the session hook fetched when the session began, if any, the claim push of step 4 records no upstream, and the released branch step 4 carries work on from is never fetched. The board is the file STATE.md on the branch `board`, which the session hook prints too; a docs/agents/STATE.md on the default branch, where the repository has one, only describes it. Take an issue the Given to workers section gives you first; else one the Queue section shows as unclaimed, labelled todo, with no open blocker in its way, one in your area first when you have one. An issue with a branch `claude/N` on origin or a file `docs/agents/claims/N.md` on the default branch belongs to another worker, and so does an issue another worker's label names, unless yours names it too: an issue given to several workers is each of theirs, and the first to claim it holds it. Read the Overlaps section too: open work that already changes the files the issue needs lands in the order it shows, so keep out of those files where the issue allows.
2. Branch from the default branch, with no upstream: `git switch -c claude/N --no-track origin/D`. Without `--no-track` the branch would track origin/D, and wherever git's `push.default` is `upstream` (or its old name `tracking`), `git push -u origin claude/N` and every later push from the branch would write D and never make claude/N; the push guard cannot see that, since it reads the command and not git's settings. The claim push of step 4 gives the branch its upstream, origin/claude/N.
3. Write the claim file `docs/agents/claims/N.md` from the template in docs/agents/claims/README.md: `- Worker: NAME`, the plan in a few sentences, the files you expect to touch, the issue's link.
4. Commit it alone, as the branch's first commit, and push: `git add docs/agents/claims/N.md`, `git commit -m "Claim #N"`, `git push -u origin claude/N`. Never with force. If the issue was released before, the board's comment on it names the branch that keeps the earlier work, `released/N-<sha>`, and the coordinator's release comment says what it holds and what its plan was: read it, and carry on what is worth keeping in commits after your claim commit (cherry-pick the commits that follow its own claim commit, or copy the files), keeping your own claim file.
5. If the push is refused because the branch exists, another worker claimed it between your fetch and your push. Delete your local branch (`git switch D`, then `git branch -D claude/N`) and go back to step 1 with another issue.
6. Announce it on the issue: add the label claimed and your label worker:NAME, take off every other worker's label (worker:<other>, or the older account:<other> or agent:<other>), one an earlier claim left or one that gave the issue to several workers, so that from here on the labels name the holder alone, as the claim file does, and post the plan as a comment. Make your label first if the repository does not have it yet, since `gh issue edit --add-label` adds none of the labels it is given when one of them is missing: `gh label create worker:NAME --color c5def5`, which says so and changes nothing when the label is already there. With gh: `gh issue edit N --add-label claimed,worker:NAME` (with `--remove-label worker:<other>` for a label left behind) and `gh issue comment N --body-file docs/agents/claims/N.md`; without it, the issue's page.
7. Open a draft pull request at once from `claude/N` to D, with "Closes #N" in its body, so the board lists the work from its first minute: `gh pr create --draft --base D --title "..." --body "Closes #N"`. Push often, naming the branch: `git push origin claude/N`. When the board comments "main moved", bring `origin/D` in: rebase on it and force your branch over origin's, the one forced push the protocol allows, and only on this branch; or merge it in, which needs no forced push. To rebase, push what the branch holds (`git push origin claude/N`) and note its tip (`git rev-parse claude/N`); then `git fetch origin`, `git rebase origin/D` and `git push --force-with-lease=claude/N:<that tip> origin claude/N`. The lease names the tip you pushed because the fetch has just moved origin/claude/N to whatever origin holds, and a lease that names none holds against that: it would force over anything pushed there since, such as a new claim of the issue after yours was released; with the tip named, git refuses the push instead. Name the branch in every push: where `push.default` is `matching`, a push that names none sends every branch that has a namesake on origin, and a forced one forces a stale local D over origin's.
8. Finishing is in PROTOCOL.md: the pull request deletes the claim file, says "Closes #N", passes the repository's checks (`bash scripts/check.sh` where it has that script) and is marked ready; the issue gets the label in-review. The owner merges, or, where your file says `"lands": "auto-merge"`, you turn on auto-merge (`gh pr merge --auto --merge`) and GitHub merges once the check is green; where the default branch requires no check, that command merges at once, so leave the merge to the owner there. The merge closes the issue.
