# A new project, from Claude Code

One command makes the repository, the Symphony Apps fill it with the whole template by pull request, and a cloud session opens on it. The person stays here and opens the browser twice, because GitHub lets no API install an App: once for the two Symphony Apps and the form's Create, once for the Claude GitHub App. OWNER/NAME stands for the repository. The person's gh is signed in (`gh auth status`) as an account that may make repositories under OWNER; a cloud session cannot run steps 1 and 2 (its GitHub proxy refuses them), so run this on the person's own computer.

1. **Make the repository, with a first commit**, since the adoption needs one; the README it makes is replaced by the template's: `gh repo create OWNER/NAME --private --add-readme --description "A Symphony project"`. Use `--public` where the plan enforces branch rules only on a public repository (GitHub Free outside an organization of the enterprise; the template's docs/setup/tiers.md). Then read the two ids the install links take: `OWNER_ID=$(gh api users/OWNER --jq .id)` (an organization answers at the same path) and `REPO_ID=$(gh api repos/OWNER/NAME --jq .id)`.

2. **See whether SymphonyBoard already reaches the repository**: `gh api user/installations --jq '.installations[] | select(.app_slug == "symphonyboard") | [.id, .account.login, .repository_selection] | @tsv'`. An installation on OWNER with `all` reaches it; with `selected`, `gh api user/installations/ID/repositories --jq '.repositories[].full_name'` says whether NAME is on its list.

3. **Hand the person one link to open, and wait for them.** The link carries the repository, so every page comes with it already chosen, and the state parameter carries its name to the form.
   - SymphonyBoard does not reach it yet: `https://github.com/apps/symphonyboard/installations/new/permissions?target_id=OWNER_ID&suggested_target_id=OWNER_ID&repository_ids[]=REPO_ID&state=OWNER/NAME`. GitHub installs SymphonyBoard on that one repository, sends the person on to Symphony Setup's install page (the Symphony browser extension carries the selection to it; without the extension the person picks the repository there), and that install sends them to the form with the repository filled in. They press Create, with Kind on Auto and Merge on "Merge the pull request for me".
   - SymphonyBoard reaches it already: `https://github.com/apps/symphony-setup/installations/new/permissions?suggested_target_id=OWNER_ID&repository_ids[]=REPO_ID&state=OWNER/NAME`, which lands on the form the same way. Never give the SymphonyBoard link to an account that has it on all repositories: an installation has one repository list, and the link would narrow it to this one repository. On an organization whose installation is "Only select repositories", the person adds the repository under Configure at `https://github.com/organizations/OWNER/settings/installations` first, then opens the Symphony Setup link.

4. **Wait for the pull request and its merge**: every twenty seconds, for up to five minutes, `gh pr list --repo OWNER/NAME --head symphony/adopt --state all --json number,state,mergedAt`. Merged: go on to step 5. Open, because the person chose to review it: say so and stop; they merge it at its page, or ask you to (`gh pr merge N --repo OWNER/NAME --merge --delete-branch`). Nothing after five minutes: the run refused the request and said why on it, at `https://github.com/OpenSpineConsortium/symphony-start/issues?q=is%3Aissue+author%3A%40me`; read the answer to the person and do what it says. The sweep is the fallback: an account with SymphonyBoard on all its repositories gets the pull request within about an hour without the form, with no settings applied and the pull request left open; then merge it, clone, and run `bash scripts/setup-repo.sh` from the clone for the settings and the topic.

5. **Install the Claude GitHub App**, which lets the cloud clone the repository itself and pushes every cloud session's work: clone and run `/install-github-app` in Claude Code (`gh repo clone OWNER/NAME && cd NAME && claude`), pick the repository, and choose "Skip for now" when it offers the Actions setup, since the token for @claude is a later choice (the template's docs/setup/claude-action.md); or give the person `https://github.com/apps/claude/installations/new/permissions?target_id=OWNER_ID&repository_ids[]=REPO_ID`. Without the App, `claude --cloud` still works by bundling the clone and uploading it, and `/web-setup` lends the session the person's gh token instead; the App is the cleaner way. The merge also opened the issue "Set up this project" in the repository, whose checklist is the rest of the setup; the first cloud session can take it.

6. **Open the cloud session**, from the clone with nothing unpushed, since the cloud clones the remote's branch and not the checkout; pick the environment once with `/remote-env` inside `claude`, then: `claude --cloud "Read the board, take the next issue as docs/agents/routines/worker.md's steps 2 to 5 say, claim it with the claim skill and carry it to a ready pull request; work on the branch claude/<issue>, not this session's own branch. gh issue and gh pr are refused in a cloud session, so add the labels, post the plan and open the draft pull request with your GitHub tools or gh api. Mark the pull request ready with your GitHub tool update_pull_request (draft false), not gh api. Do not merge."`. It creates the session on claude.ai and returns; the person opens it at https://claude.ai/code or in the Claude app. Each further `claude --cloud` is another session on the same repository, and the board keeps them apart. Or give the person the link that fills the box at claude.ai/code: `python3 -c 'import sys, urllib.parse as p; print("https://claude.ai/code?" + p.urlencode({"prompt": sys.argv[1], "repositories": sys.argv[2]}, safe="/", quote_via=p.quote))' "PROMPT" "OWNER/NAME"`; nothing starts until they send.

7. **A Project, for many threads on one repository.** At https://claude.ai/code (Pro and Max; the beta reaches accounts gradually), the person makes a Project and links OWNER/NAME as its only resource, leaving its instructions, description and memory blank: every thread of it is a cloud session that starts from a fresh clone and reads the repository's CLAUDE.md, memory and board, so nothing is copied into the Project (the template's docs/setup/claude-project.md). A message in the Project's conversation starts a thread per task, threads run in parallel, and the board keeps them apart, each on its own issue; a session started with `claude --cloud` moves into the Project from its menu ("Move to project"); the worker routine is made inside the Project (docs/agents/routines/worker.md). A Project belongs to one account and cannot be shared, and no command or API makes one: claude.ai alone does. What is shared is the repository: another person works it from a Project of their own, on their own account and plan, once they have Write on it (`gh api -X PUT repos/OWNER/NAME/collaborators/LOGIN -f permission=push`) and the Claude GitHub App's installation reaches it; take the secrets out of the repository first (docs/start/team.md, step 1).
